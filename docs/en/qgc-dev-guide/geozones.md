# Geozones

The geozone module loads UAS geographical zones (ED-269, ED-318, AIXM 5.1, FAA TFRs and airspace layers, DiPUL, IGN and OpenAIP), shows them on the maps, checks missions and guided commands against them and alerts in flight.
This page describes how the module is built, for developers changing it. What it does for users is described in the [Geozones user guide](../qgc-user-guide/geozones/geozones.md).
The data providers which were evaluated, the data a provider must supply and the user flows are compared in [Geozone Data Providers](geozones-providers.md).

## Data Flow {#data-flow}

```txt
 file ─────────────────────────────────────────────┐
 feed or service ─► GeoZoneFeedFetch (GUI thread)  │   token, dataset link, download, all pages,
                    with GeoZoneDownloader         │   companions, SHA-256, conditional requests
                                                   ▼
                    GeoZoneLoader::run (worker thread)
                      unzip ─► GeoZoneParseCache (current?) ─► GeoZoneParser ─► GeoZoneFormat
                      stored copy and cache written to GeoZoneStore
                                                   ▼
          GeoZoneSourceRepository (GUI thread): GeoZoneSource, GeoZoneSourceIndex (sources.json)
                                                   ▼
          GeoZoneManager: GeoZoneCatalog::rebuild() with its GeoZoneIndex, zonesChanged()
                                                   ▼  catalog copies
   GeoZonePathEvaluator: GeoZoneMissionCheck, GeoZoneProfile, GeoZoneRouteSearch, GeoZoneGuidedCheck,
                         GeoZoneBriefing, GeoZoneFences
   GeoZoneMonitor ─► GeoZoneVehicleMonitor ─► GeoZoneAlertTracker; GeoZoneAlertArbiter
   GeoZoneMapModel ─► GeoZoneMapLayer
```

1. `GeoZoneSourceRepository` adds, loads, refreshes and removes the sources. Each load or fetch of a source gets a new `GeoZoneCancelToken`, which cancels the previous one of the same source; removing a source or closing the application cancels its token too. Every stage checks the token and drops its result once it is canceled.
1. Feeds and services are downloaded by a `GeoZoneFeedFetch`, in stages: the OAuth2 token of the service, the feed URL (which may be a page linking to the current dataset, see `GeoZoneProviders::datasetLink`), the dataset, the further pages of a response the server limited (WFS `STARTINDEX`, ArcGIS `resultOffset` or numbered pages, see `GeoZoneProviders::paging`), and the companion documents the format refers to (like the NOTAM details of FAA TFRs). A response still limited after `maxWfsPages` further pages fails the fetch (`Paging::truncated`), except a WFS response, which tells how many zones are missing: its pages are loaded, and `GeoZoneSource::incompleteText()`, reported by `errorString()`, makes it count as a failed refresh for the scheduler and for geo-awareness, like a WFS response which lost a page (`GeoZoneRepositoryTest::_testPageCap()`). The document is checked against the SHA-256 its publisher gives. `GeoZoneRefreshScheduler` decides when feeds are fetched again: after the refresh interval, retries after failures, and with the network state `GeoZoneManager::watchNetwork()` reads from `QNetworkInformation` (`GeoZoneSourceRepository::setNetwork()`): offline, due feeds wait for the network (`waitingForNetwork()`); back online, feeds which failed because no server answered (`GeoZoneDownloader::Result::unreachable`) are retried at once, and such failures are retried at least every `maxUnreachableRetrySecs`. Each source shows its next check (`GeoZoneSource::nextCheckText()`). `GeoZoneRepositoryTest::_testRefreshAfterOffline()` tests it.
1. `GeoZoneLoader::run()` reads the file or download on a worker thread: it puts the pages of a paged response together (a page which can't be read, or a merged document which can't be written, fails the load instead of storing a response which misses zones, `GeoZoneRepositoryTest::_testPageMerge()`), extracts zip archives, restores the result from the `GeoZoneParseCache` when the file is a stored copy whose cache is current, or else parses it with `GeoZoneParser`, which detects the `GeoZoneFormat` and parses the features, and writes the stored copy and its cache with a copy of the `GeoZoneStore`. The cache is keyed with the format hint the copy is restored with at the next start (the one of its address, `GeoZoneLoader::storedJob()`), not with the hint of the load which wrote it, like the format of the zones a refresh was given: otherwise every start after a refresh would parse the copy again (`GeoZoneParserTest::_testParseCacheAfterRefresh()`).
1. Back on the GUI thread, the repository replaces the zones of the `GeoZoneSource` and saves the index of the sources (`GeoZoneSourceIndex`). `GeoZoneManager` then rebuilds the `GeoZoneCatalog` from the sources turned on and emits `zonesChanged()`. The catalog keeps a zone which several sources publish alike (`GeoZoneCatalog::sameContent`) once, from the first source, and lists the others in `GeoZone::otherSources`, so that all its consumers (maps, checks, alerts, search, fences) get it once; filters showing the zones of one source use `GeoZone::fromSource`, while code forgetting the zones a source is about to delete compares `GeoZone::sourceKey`. Alert states, approvals, fences and saved plans refer to a zone by `GeoZone::key()`: its source, identifier, name and restriction, which stay the same over reloads. Where a source has several zones with the same ones, the first by content hash keeps that key and the others get an ordinal appended (`GeoZone::disambiguateKeys()`), so keys are unique and don't depend on the order of the file.
1. The checks take a copy of the catalog. `GeoZonePathEvaluator` evaluates paths against it for the mission check, the altitude profile, the guided command checks, the route search, the briefing and the fence import, so that they agree; `GeoZonePolicy` selects the zones each of them applies to. The monitor evaluates the vehicle positions every second with `GeoZoneAlertTracker`, and the maps query the shapes in their view.
1. Each map's `GeoZoneMapModel` applies the map filters of `GeoZoneDisplay` (restrictions, altitudes, schedule and source, kept in `GeoZoneSettings`, see `GeoZoneMapFilter` with its `altitudeMargin` and `scheduleHours`) while it selects the shapes, caching the result per zone until the filters, the altitudes, the time or the zones change, so that panning stays fast with many zones. The altitude filter compares the zone limits with a `GeoZoneAltitudeRange`: the altitudes of the mission (`GeoZoneMissionPath`) of its `missionController` in the Plan View, or the altitude of the active vehicle (`GeoZoneVehicleMonitor::vehiclePosition`, read every second) with `vehicleAltitudes` in the Fly View. The `keptZones` and `highlightedZones`, which the views set to the zones the mission check and the flight alerts report, are never hidden. Filters only change the maps; `zonesAt()` of the model gives the zones shown at map clicks, and `filteredZoneCount` the zones in view the filters hide, for the hint with the reset. The model hands its `GeoZoneMapLayer` the shapes to draw (`shapes()` at `detailLevel()`, signalled by `shapesChanged()` before shapes left out may be deleted); the layer keeps their triangulations for the last few detail levels while they are shown.

## Mission Path {#mission-path}

The Plan View checks see the mission as a `GeoZoneMissionPath`: the segments flown with their altitudes and terrain, the areas of patterns, the legs between the items, the paths besides the drawn flight path and the contingency paths, see the [user guide](../qgc-user-guide/geozones/geozones.md#mission-check). It is built on the GUI thread, then only read, so that the checks can run on worker threads. The parts:

- `GeoZoneMissionReader` (`src/GeoZone/Planning`) is the only part reading the `MissionController`: `path()` reads it the way it draws the flight path (in `_recalcFlightPathSegments`), each item as a `GeoZoneMissionPathBuilder::Item` with its `GeoZoneMissionItem`, its drawn segments, the segment to the next item with a coordinate, the area of patterns, its loiter circle and VTOL transition, and the plan's home, rally points and breach return point. `items()` lists the items as `GeoZoneMissionItem`s and `returnParameters()` reads the vehicle's return parameters.
- `GeoZoneMissionPathBuilder::build()` (core) makes the path of these items without the application: the legs between the items, nothing after the first **Return To Launch** but the segment home, the flight following the **DO_JUMP** items, the paths the drawn flight path leaves out (loiter circles, VTOL transitions, the loiter of landing patterns, the return after a **Return To Launch**) and the contingency paths.
- `GeoZoneMissionJumps` (core) walks the items like the vehicle with their **DO_JUMP** items, a pure computation on the items and the indexes and lengths of the drawn segments.
- `GeoZoneReturnDestinations::fromMission()` (core) finds where the vehicle can return to from the items and the plan's home, rally points and breach return point, given as plain positions: the first waypoint after the takeoff, the landing sequences and the return path, for `GeoZoneReturnModel`. `GeoZoneMissionReader` calls it with the plan of a `MissionController`, other checks can call it with their own. `GeoZoneReturnTest` tests it headless.
- `GeoZoneMissionPath` (core) keeps the result and computes the connected paths of the segments, the times along them and the labels of the paths.

`GeoZoneMissionPathTest` tests the core parts headless, and the reading of missions in _QGroundControl_.

## Operational Intent {#operational-intent}

`GeoZoneOperationalIntent` (core) builds the 4D volumes of an operational intent from evaluator paths with times, see the [user guide](../qgc-user-guide/geozones/geozones.md#operational-intent), and writes them with the field names of the ASTM F3548-21 API definition (`OperationalIntentDetails`, `Volume4D`, `Volume3D`, `Polygon`, `Circle`, `Altitude`, `Time` of [utm.yaml](https://github.com/astm-utm/Protocol/blob/master/utm.yaml)). `buildVolumes()`:

1. Splits the paths into legs, cut along their great circles every 1 km so that the straight lines of the projection stay close to them, with the altitudes above the WGS84 ellipsoid (`GeoZoneGeometry::geoidHeight()`) and the times interpolated. Legs with an unknown altitude span the altitudes of the flight; paths without times (no planned start) or without any altitude fail.
2. Orders the legs by time and merges adjacent ones greedily with a priority queue. The cost of a merge is how much it adds to the sum of the 4D extents of the volumes: the area of the convex hull widened by the buffer (Steiner's formula: area + perimeter × buffer + π × buffer²) times the height and the duration with the buffers. Merges which don't add to it are always made, like those of the short pieces of a straight leg or of the lines of a survey; then the cheapest until at most `maxVolumes` remain. Because the time buffer dominates the durations, two parts of a straight leg merge while the product of their lengths is at most π r T v / 2 (r the horizontal buffer, T the time buffer, v the speed), into volumes of up to about 1.7 km at 10 m/s with the defaults.
3. Writes each group as the convex hull of 16-gons circumscribing the buffer, widened by `bufferMargin` (1 %) and placed with `QGeoCoordinate::atDistanceAndAzimuth()` around each hull position, so that the buffer is true in meters whatever the latitude; the hull is taken in the equirectangular `LocalProjection` of the flight, which is affine in latitude and longitude, and its edges are cut every 1 km so that they stay near the geodesics of the standard. A group at one position becomes a circle. Altitudes and times are rounded outward.

Since the hulls are convex and contain the buffered positions of their legs, every merge keeps the path contained: `GeoZoneIntentTest::_testVolumes` checks it for straight and turning paths, surveys, climbs, long legs, the antimeridian, high latitudes, loiters and random walks capped to few volumes, and `_testJson` the field names and enumerations of the schemas. `GeoZoneOperationalIntentExport` (application) builds the paths with `GeoZoneMissionPath::evaluatorPaths()` from the planned flight times, takes the parameters from `GeoZoneSettings` (`intent*`) and adds the U-space airspaces and authorisations of the zones the mission check's evaluation finds entered while active.

## Geometry {#geometry}

The planar geometry is in namespace `GeoZoneGeometry`, split into units which `GeoZoneGeometry.h` includes together:

| Unit | Contents |
| ---- | -------- |
| `GeoZoneProjection` | `LocalProjection`, the equirectangular projection to meters around an origin which the other units work in. It is affine in latitude and longitude, so edges straight in latitude and longitude stay straight. |
| `GeoZonePredicates` | Containment, intersection, distance and interval tests of rings and polygons. Rings are filled with the non-zero winding rule by default, so the areas a zone boundary crossing itself encloses twice are inside, holes only exclude what they enclose an odd number of times, and points on a boundary (within `kBoundaryTolerance`) are inside, like for the segment intervals. Fences pass `Qt::OddEvenFill`, the rule of the autopilots. The distance to a segment (`distanceToSegment()`, `distanceToSegmentSquared()`) and the test for an edge folding back over the previous one (`foldsBack()`) are here once, for the code which needs them. |
| `GeoZoneSimplify` | `simplifyOutward()`, which reduces polygons for fences and route obstacles while keeping the zone inside, and `simplifyChain()`, the Douglas-Peucker step it shares with the simplification of the map shapes (`GeoZoneShape::simplifyRing()`). |
| `GeoZoneGreatCircle` | Great circles: densifying zone edges published as geodesics, and `greatCircleFractions()`, which splits the legs of paths into pieces within `kPathGreatCircleToleranceMeters` of the great circle the vehicle flies. The evaluator adds positions there, and `GeoZone::horizontalIntervals()` and `pathEntry()` check long segments in such pieces. `pathEntry()`, which the flight alerts call for each nearby zone every second, first leaves out the segments whose great circle stays outside the box of the zone (`greatCircleLatitudes()` bounds its bulge towards the pole without cutting it), then cuts a segment into its pieces once for all volumes of the zone. |
| `GeoZoneGeoid` | The EGM96 geoid heights. |

`GeoZoneVector.h` has the inline planar vector helpers (`cross`, `dot`, `length`, `unit`, `orientation`) the units share.

## Vertical Limits {#vertical-limits}

`GeoZoneVertical` converts the published limits of a volume to heights comparable with altitudes above mean sea level and compares them, for `GeoZone`, the evaluator, the alerts, the profile and the route search. Limits above ground subtract the terrain elevation from the altitudes, limits above the WGS84 ellipsoid add the EGM96 geoid height, and flight levels are converted with the QNH, then floors are lowered and ceilings raised by `GeoZoneVertical::flightLevelMargin`.

There is one policy for what isn't known, in `GeoZoneVertical::bound()`: a limit bounds the volume only when it can be compared. A limit in an unknown reference, a limit above ground where the terrain is unknown, or any limit compared with an unknown altitude doesn't bound it, so the volume extends over all altitudes on that side and unknowns count as inside. Floors at the ground and the published unlimited ceiling don't bound it either. New comparisons should go through `bound()` rather than read the limits. `GeoZoneVertical::approximations()` tells why a comparison is approximate, which `GeoZonePathEvaluator` turns into the `Approximation` flags of its crossings, stretches and results, together with the flags of the paths (`TerrainCoarse`, `GreatCircleDeviation`) and schedules (`ScheduleAssumed`, see `GeoZone::scheduleAssumed()`). The briefing and the mission check warning report them; keep `approximationTexts()` and `approximationCodes()` in step with new flags.

## Threading Model {#threading}

- The GUI thread owns the manager, the repository, the sources, the downloads (`GeoZoneFeedFetch`, `GeoZoneDownloader`), the refresh scheduler, the monitor and the map models. `GeoZone::active` is updated there and read from other threads as an atomic. The text naming the source of a zone (`GeoZone::sourceText()`) is kept in a `GeoZoneSourceLabel` which the zones of one load share with their `GeoZoneSource`: when a download confirms them current (`markCurrent()`), the source rewrites the label under its mutex instead of a field of each published zone, and the zones listing that source in `GeoZone::otherSources` show the new text too.
- Long work runs with `QtConcurrent::run` on the global thread pool: `GeoZoneLoader::run`, `GeoZoneMissionCheck::evaluate`, the bands of `GeoZoneProfile` and the searches of `GeoZoneRoutePlanner` (which reports progress and can be canceled). Their results come back through a `QFutureWatcher` and are dropped when outdated: loads check their cancel token, and the mission check, the profile and the route planner share a `GeoZoneMissionWorker` (`src/GeoZone/Planning`).
- `GeoZoneMissionWorker` follows the signals of the `MissionController` after which the mission changes, and the changes its owner reports with `schedule()`, for a delay (half a second) before `triggered()` asks the owner to start an evaluation. `run()` starts a new generation and evaluates on the thread pool, `watch()` adds a computation to the current generation (like another round of the route search, with its progress), and `runNow()` evaluates on the GUI thread. `invalidate()` and `stop()` outdate the running evaluations, whose results are dropped and whose `cancelToken()` is canceled; the owners call them when the zones are about to change. `settled()` tells whether the owner's result is that of its current inputs. Saving a plan (`GeoZonePlanData::save()`) reuses the result of the Plan View's `GeoZoneMissionCheck` when it is settled (`GeoZoneMissionCheck::settledCheck()`), and otherwise evaluates the mission on the GUI thread with `evaluatePlan()` and `classify()`, which have no side effects like setting the area of interest.
- Workers only get values: a `GeoZoneCatalog` copy, which is immutable and keeps its zones alive through shared pointers while the sources change (but not the shapes, which only the maps use), a `GeoZoneMissionPath` built on the GUI thread, and the job or settings of the computation. `GeoZoneStore` methods only access files, so a copy can be used from a worker.
- Caches filled on first use from any thread are guarded: the simplified exclusion polygons of a `GeoZone` (`_simplifiedMutex`, the last `simplifiedCacheSize` tolerances rounded to `simplifiedCacheResolution`) and its local projection (`std::once_flag`). Results computed outside the lock are only added when no other thread added them meanwhile. `GeoZoneIndex` queries don't modify the index.
- An evaluator copy can run on any thread, unless its policy excludes authorised zones, since authorisations are only looked up on the GUI thread, or its terrain lookup, which is called from the evaluating thread, needs the GUI thread. Formats are stateless and parse on worker threads; `parseXml()` stops between features once `GeoZoneParserUtils::cancelled()`.
- A scoped authorisation is checked against its scope zone (`GeoZoneAuthorisation::scopeZone()`), which every position asks for: the authorisation keeps the one it made (`ScopeCache`, behind a mutex) while the zone, recognized by its content hash, and the ceiling and area are the same. The cache is no part of the value: it doesn't take part in comparisons and a copy starts without it (`GeoZoneEvaluatorTest::_testAuthorisationScopeKept()`).

## Route Search {#route-search}

`GeoZoneRouteSearch` (`src/GeoZone/Core/Route`) is the facade `GeoZoneRoutePlanner` uses: `plan()` searches a detour, a climb and a descent for a leg and sorts them by cost. Its parts are internal to the core:

- `GeoZoneRouteObstacles`: the zone volumes a detour keeps the margin from, in a local projection around the leg. Their outlines are only projected, detailed ones simplified outward except near the ends of the leg, when a query comes near them, and their edges are put in a `GeoZoneRouteGrid` of cells which finds those near a segment. It tells whether a segment or a point keeps the margin, and where the nodes around the convex corners of an obstacle are.
- `GeoZoneRouteGraph`: the visibility graph of a detour, its nodes, the cache of the visibility of its edges and the A* search of its shortest paths, which tests an edge only when it would reach a node first (Lazy Weighted A*).
- `GeoZoneRouteDetour`: the rounds of a detour search, each adding to the graph the zones the path ran into, until it runs into none, and its outcome.
- `GeoZoneRouteVertical`: the samples of the leg with their terrain, and the climbs over and descents under the zones.

The units use the planar vector helpers of `GeoZoneVector.h` shared with the geometry.

The work of a search is bounded. Testing the edges from each node to all others takes time growing with the square of the nodes, a minute of a debug build for a maze of 1200 zones. Graphs of more than 1000 nodes are therefore first searched along the edges to the near nodes only (those of the grid cells around a node, at least 32 nodes of 8 obstacles, and the end), combining edges like Theta* where a node sees the one before the previous, and the path is then straightened; all edges are searched when that finds no path, except by the search of detours up to 1.3 times the leg, which then leaves it to the search with the full length limit. Each graph counts its work, the edges and nodes considered and the visibility tests weighted by 16, and its searches stop with `Failure::SearchLimit` at `Settings::maxSearchWork`, as they do after 64 rounds or at 20000 nodes. `GeoZoneRouteTest::_testMaze` checks the time, the work and the length of a detour through a maze, which `GeoZoneBenchmark::_benchmarkRouteSearchMaze` measures.

## Flight Alerts {#flight-alerts}

`GeoZoneMonitor` (the `GeoZoneMonitor` QML singleton) monitors the vehicles on the GUI thread:

- Each `Vehicle` gets a `GeoZoneVehicleMonitor`, keyed by the object (a reconnecting vehicle starts clean) and by a `key` unique for the session. Positions which don't come from a `Vehicle`, like those of tests and tools, are passed to `evaluate(position, vehicleId)` and get a monitor per vehicle id. `evaluateVehicles()` runs every second: `GeoZoneVehicleMonitor::update()` evaluates the vehicle's position with its `GeoZoneAlertTracker`, or marks the position unavailable when the coordinate is invalid, the link lost or the position stale. It also records where the terrain below the vehicle comes from (`TerrainSource`): the vehicle's height above terrain, the ground for a disarmed vehicle, or `GeoZoneTerrain` (`altitudeDegraded()`). The tracker's `Limits` are the vehicle's alert thresholds at each evaluation: `GeoZoneVehicleThresholds` picks the manufacturer's `GeoZoneAlertThresholds::Profile` from the MAVLink vehicle type, keeps the GNSS accuracy of `GPS_RAW_INT` (`h_acc`, `v_acc`, HDOP) and `HIGH_LATENCY2`, and computes the thresholds at the velocity with the pilot's extras of the settings (`Context::extras`); tests fix the limits with `Settings::limits`. The vehicle monitor publishes them as `alertThresholds`.
- The `GeoZoneVehicleMonitor` of the active vehicle is `GeoZoneMonitor.activeVehicle` in QML (`activeMonitor()`, null without, `activeMonitorChanged()` when another vehicle becomes active, so QML guards it with `?.`). Its properties are the nearby zones as `nearbyModel`, `keptZones` (the nearby zones and the predicted entry, which the map filters don't hide), the vertical bands, altitude and terrain, `positionUnavailable` (the zones and bands are then stale), `altitudeDegraded`, the predicted entry and the fence status.
- Each alert is an `AlertEvent` (`Approach`, `Entry`, `Activated` when the tracker finds the vehicle was already inside the zone at its previous position, before the zone applied, `ActivationSoon` from the `GeoZoneActivationTracker` of each vehicle, which looks for the inactive zones within its approach distances that become active within the caution time and alerts each activation once, `PositionLost` or `Traffic`), emitted as `alertEvent()` for `GeoZoneAlertHistory` and as `alert()`, added to the `GeoZoneAlertModel` the popup shows (`GeoZoneMonitor.alerts`) and submitted to the `GeoZoneAlertArbiter`.
- Alerts have a `GeoZoneAlertLevel` (`Warning`, `Caution`, `Advisory`, after EN 4709-003 Annex D; registered in QML as `GeoZoneAlertLevel`), set by `GeoZoneMonitor::alertLevel()` / `zoneLevel()` or given to `raiseVehicleAlert()`. Severities sort by level first (`GeoZoneAlertLevel::severity()`), so the model, the arbiter and the spoken order follow the levels; the arbiter starts each level of a message with its word (`spokenPrefix()`), the model has `level`/`levelText` roles and the highest `level`, the history a `level` role and log column. `GeoZoneMonitor.activeLevel` and `predictionLevel` give the level of the active vehicle where it is and of its predicted entry, for the indicator and the map; `GeoZoneStyle.levelColor()` the colors. Approaches whose predicted entry is within `GeoZoneAlertTracker::Limits::imminentTime` (the reaction time and the evaluation interval) raise a second, imminent approach alert, a warning.
- `GeoZoneAlertArbiter` only keeps the state of the alerts and decides the announcements: the pending alerts, the breaches (entries into prohibited zones, repeated every 30 s until acknowledged or left), the mute (which only silences the speech: muted repeats are still shown), the zones approved per vehicle until it leaves them and their approach range (`approveZone()`) and the vehicles whose position is lost, whose breaches are suspended. The monitor calls `tick()` after each evaluation, emits `alertRepeated()` for the repeats of the announcement and passes its text to the `GeoZoneMonitor::AudioSink` (`AudioOutput` in the application, `setAudioSink()` in tests) only when spoken alerts are on. So repeats, acknowledgements and mutes behave the same without speech.
- When a vehicle's position becomes unavailable, the monitor suspends its breaches, doesn't pass the zones of its last position to `setInsideZones()`, and raises one `PositionLost` alert for the most restrictive nearby zone. The next position resumes the breaches, or ends them if the vehicle left. `positionLost(vehicleId)` does the same for position monitors.
- `GeoZoneAlertModel` holds the shown alerts, the most severe first, with their actions as roles, updated after each evaluation and notified only when they change: `question` (an approach or entry of a vehicle into a restricted zone, `GeoZoneMonitor::asksPermission()`, while the vehicle is still in or near the zone), `activeVehicle`, `inside` and `climbHeight` (how far the vehicle climbs to be `climbClearance` above the zone's ceiling), with `questionCount` and the highest `climbHeight` of the active vehicle. `approveAlert()` ("I do") acknowledges the alerts about the zone and approves it in the arbiter, `dismissAlert()` acknowledges one alert, `closeAlerts()` closes the popup. The popup runs Hold, Return and Climb Above Ceiling through `globals.guidedControllerFlyView.confirmAction()`, the confirmation of the Fly View's own guided actions.
- What the pilot is shown and answers is logged after the alert as pilot events (`AlertEvent::Notified`, `Approved`, `Dismissed`, `Muted`, see `pilotEvent()`) with the id of the alert, through `GeoZoneAlertHistory::logPilotEvent()`: they are written to the CSV log but not listed with the alerts, also when the log is read back.
- While traffic is checked, the application monitor passes the traffic of `ADSBVehicleManager` to `evaluateTraffic()` after the vehicles of each evaluation, which checks the closest 100 aircraft within `trafficRadius()` (10 km) of the active vehicle against the zones, with a `GeoZoneAlertTracker` per ICAO address, and publishes those in or near zones as `GeoZoneMonitor.traffic`. Tests pass the aircraft directly. Entries become `Traffic` alerts whose severity is raised by `trafficSeverity`, so they are shown after those of the vehicles, and are never submitted to the arbiter, so never spoken.
- `GeoZoneAlertHistory` keeps the `AlertEvent`s for the indicator and, once `startLog()` is called (by the application monitor only), logs them: it buffers their CSV lines (`logLine()`, read back by `parseLogLine()`) and writes them to the open file of the day every 2 s (`flushLog()` writes them at once), and deletes the files older than the `recordRetention` setting (kept forever by default) when it starts a file. `startLog()` first adds the alerts logged earlier today.
- `GeoZoneFlightRecorder` (created by `GeoZoneModule::init()`) records each flight from arming to disarming: a downsampled track, the `AlertEvent`s raised and the planned start. On disarm it builds a `GeoZoneBriefing` of the track with its sample times (schedule tolerance 0), writes it with `GeoZoneBriefingExport::toJson()`, replacing `mission` by `flight` and adding `track`, `permits` and `alerts`, the rows of the vehicle in the alert log read back through `GeoZoneAlertHistory::logFields()` by the columns of each file's header, so rows the popup logs (the pilot's answers) are included without the recorder knowing them. Tests call `start()`, `addPosition()` and `finish()` with a fake clock.
- `GeoZoneConformance` (the `GeoZoneConformance` QML singleton) builds the `GeoZoneOperationalIntent` volumes of the Fly View mission (passed by `GeoZonePlanData::follow()` through `followFlyViewPlan()`) while there is a planned start, and checks the active vehicle against those of the current time every second (`check()`, with the altitude converted to the ellipsoid). Leaving them raises a `NonConformance` alert through `GeoZoneMonitor::raiseVehicleAlert()`, which shows, logs and announces alerts which aren't about a catalog zone. Tests set the volumes and call `evaluate()` with a fake clock.
- Each `GeoZoneVehicleMonitor` of a `Vehicle` owns a `GeoZoneFenceWarning` (`fenceWarning` in QML), which follows the vehicle's fence (its `GeoFenceManager` and the fence parameters, `vehicleConfig()`, or `setConfig()` in tests) and checks each `GLOBAL_POSITION_INT`, at most every 250 ms, with `GeoZoneFencePrediction::predict()`: a breach within `warningTime()` (the `pilotReactionTime` of the vehicle's alert profile plus its `fenceWarningMargin`, 8 s by default, set by `GeoZoneVehicleMonitor`) makes it `active`. The monitor shows it as an alert of severity -1 whose message counts down in place, submits it to the arbiter once (spoken) and logs `AlertEvent::FenceWarning`; `FENCE_STATUS` breaches are logged as `FenceBreach`. `takeControl()`, `disableFence()` and `enableFence()` override the fence action for `GeoZoneFenceAlert.qml`, shown in the alert popup and the indicator page.
- `GeoZonePreflightCheck` computes the items of the Geozones group of the pre-flight checklist from a `GeoZoneMissionCheck` of the Fly View plan, the sources, the QNH setting, `GeoZoneRemoteId`, the fence `GeoZoneFenceUpload::verification()` recorded per vehicle when an upload is verified, and the `GeoZoneVehicleMonitor`, awareness and permits of its `GeoZoneMonitor` (`setMonitor()`, the application monitor when created from QML). The static item functions take plain inputs for tests.
- A vehicle is on the ground when it is connected and disarmed (`GeoZoneVehicleMonitor::onGround()`, `setArmed()` for position monitors, unknown for offline vehicles and positions without). Its entries are `OnGround` alerts, and arming (the vehicle's `COMMAND_ACK` of `MAV_CMD_COMPONENT_ARM_DISARM` while on the ground, or `armedChanged`) raises them again once per `armingAlertIntervalMSecs`; `groundWarning` and `groundLevel` give the indicator, the checklist and `GeoZoneGuidedCheck::groundWarning()` the most restrictive zone it is in.
- `GeoZoneAwareness::evaluate()` turns an `Input` (the data of the manager, the vehicle's link, position and `GPS_RAW_INT` status from `GeoZoneVehicleMonitor::gnss()`) into a state with reasons; the GNSS limits (`GnssLimits`) come from the alert profile of the vehicle class (`GeoZoneAlertThresholds::Profile`). The monitor publishes the status of the active vehicle as `GeoZoneMonitor.awareness` and alerts the changes of each armed vehicle that a `GeoZoneAwareness::Tracker` lets through as `Awareness` events.
- `GeoZonePermits` (`GeoZoneMonitor.permits`) keeps the permits of the flight by `GeoZoneAuthorisations::zoneKey`. `_submit()` logs the alerts of zones with a permit with the detail `permit` and only shows entries, as advisories; `approveAlert()` acknowledges a permit instead of an arbiter approval for the zones it applies to. The monitor ends the permits of a vehicle when it disarms after having been armed or is removed (`endFlight()`), and logs `Permit` and `PermitEnded` pilot events.
- The on-ground, geo-awareness and fence alerts have the `GeoZoneAlertLevel` of the zone alerts: `GeoZoneMonitor::groundLevel()`, `GeoZoneAwareness::alertLevel()`, and warnings for the fence.

`GeoZoneMonitorTest` tests the arbiter, the speech, position loss, the alert actions, the traffic and the log with a fake clock and offline vehicles; `GeoZoneFlightTest::_testMockLinkVehicle()` flies a MockLink vehicle through the Zurich fixture, including a lost link.

## Adding a Format {#adding-a-format}

1. Add a value at the end of `GeoZoneParser::Format`, whose values are stored in the parse caches.
1. Add a class implementing `GeoZoneFormat` in `src/GeoZone/Core/Formats`, registered with `GEOZONE_REGISTER_FORMAT(Class)`, and add its instance to `GeoZoneFormat::formats()` in `GeoZoneFormat.cc` (the linker leaves out files of the static library which nothing references). List the file in `src/GeoZone/Core/CMakeLists.txt`.
1. Recognize the documents:
   - JSON formats implement `detect()`, called by `GeoZoneFormat::detectJson()` in increasing `detectionOrder()`. Formats recognized by their feature properties come before ED-318 (50), which accepts any `FeatureCollection`, and ED-269 (60). Web feature services may answer with an empty list, which only the format hinted by the URL (`GeoZoneProviders::formatHint`) accepts, with `acceptsEmpty()`.
   - XML formats return `true` from `isXml()` and implement `detectXml()` with the root element and namespace, and `parseXml()` for the whole document.
1. Convert the features: `readMetadata()` for the title, provider and issue time, and `parseFeature()` filling a `GeoZone::Data` with `GeoZoneParserUtils` (`_appendHorizontalGeometry`, `_applicability`, `_lengthUnit`, `_commonProperties`...). `parseFeature()` returns `FeatureResult::Zone` for a zone with volumes (`featureResult(zone)`), `Unusable` for a feature without usable geometry, which is counted as skipped, and `Filtered` for a feature the format leaves out on purpose, like airspace which doesn't concern drones, which isn't. For formats with `acceptsEmpty()`, a list whose features are all filtered loads like an empty one, but a list with unusable features and no zone is an error, so that a feed keeps its previous zones. Times of schedules are UTC, fixed offsets (`DailyPeriod::utcOffsetSecs`) or local times with their `QTimeZone` (`DailyPeriod::timeZone`), which keeps them right across daylight saving time changes; `_applicability` gives times without offset the time zone of the zone's country (`GeoZoneSchedule::countryTimeZone`), so it needs the country and the volumes. That time zone is only assumed (`DailyPeriod::timeZoneAssumed`), since the formats don't tell whether such times are local or UTC, so `GeoZoneSchedule` applies these periods in both. `GeoZoneParser` then checks the geometry (`_normalizeVolumes`). Report problems in `zone.issues` rather than failing the file.
1. If the features refer to other documents, implement `companionRequests()` (key, version and URL of each) and `parseFeatureWithCompanions()`; `GeoZoneFeedFetch` downloads them and stores them with the document (`GeoZoneParser::composite`), see the FAA TFR format.
1. Edges are taken straight in latitude and longitude, like GeoJSON lines. If the specification makes them geodesics, add points on their great circles with `GeoZoneParserUtils::_densifyGreatCircles()` (or `GeoZoneGeometry::densifyGreatCircles()` with a flag per edge, like the AIXM format), and turn arcs into points within `GeoZoneGeometry::kGreatCircleToleranceMeters`.
1. Return `true` from `isLive()` for short-lived restrictions refreshed and outdated after hours, and add the feeds of the format to the feed catalogue `GeoZoneFeeds.json` with its name in `GeoZoneFeedCatalogue::formatFromName()` (see [Adding a Provider or Service](#adding-a-provider)).
1. Bump `GeoZoneParser::version`, so that stored sources are parsed again instead of restored from their caches. Do the same whenever a change of the parser, a format or `GeoZoneParserUtils` changes the result for the same bytes. `GeoZoneParserTest::_testParseFixtures` compares a hash of the result of each fixture with the one recorded in `_testParseFixtures_data` for the version (`kResultHashVersion`), so it fails when the results change without a bump, and after a bump until the hashes it prints are recorded.
1. If `GeoZoneParser::Result`, `GeoZone::Data`, `GeoZone::Volume` or the schedule periods get new fields, serialize them in their `QDataStream` operators and bump `GeoZoneParseCache::formatVersion`. `GeoZoneParserTest::_testParseCacheRoundTrip` counts the fields of these structures and fails when one is added, as a reminder: set the field in `_syntheticResult`, compare it in `_resultDifference`, which the round trip of the synthetic result then checks, and update the count.
1. Add a fixture to `test/GeoZone/data/`, list it in `GEOZONE_TEST_DATA` of `test/GeoZone/CMakeLists.txt`, add a row to `GeoZoneParserTest::_testParseFixtures_data()` and a test of the zones it gives, and its edges to `_testEdgeInterpolation_data()` if they aren't straight. Document the fixture in `test/GeoZone/README.md`.
1. Add the format to the hints of `test/GeoZone/fuzz/GeoZoneFuzzJson.cc` (JSON formats) and seeds to `test/GeoZone/fuzz/seeds/` for responses the fixture doesn't cover; the fixtures are seeds too.
1. Update the [format support matrix](../qgc-user-guide/geozones/geozones.md#format-support-matrix) and the parse error messages naming the supported formats.

## Adding a Provider or Service {#adding-a-provider}

The feeds and services _QGroundControl_ knows are listed in the feed catalogue `src/GeoZone/Core/Sources/GeoZoneFeeds.json`, compiled in as the resource `:/geozone/GeoZoneFeeds.json`. Its format is documented for users in [Adding or Changing Feeds](../qgc-user-guide/geozones/geozones.md#adding-or-changing-feeds); adding a provider usually takes an entry there and no code. `GeoZoneFeedCatalogue` (`src/GeoZone/Core/Sources`) reads catalogues into `GeoZoneProviders::Service` and `GeoZoneProviders::ServiceTemplate` entries, and `GeoZoneProviders` answers from the catalogue in use:

- A national feed is an entry of `feeds` with an `id`, a `name`, its `country`, the `format` (which `formatHint()` gives for URLs of the host of its URL, or of `match.host` and `match.path` for services sharing a host, like the FAA's ArcGIS layers) and a `url`, which **Add Feed...** offers (`feedPresets()`, sorted by name, with the `note`, `licence`, `attribution` and `info` page shown when it is chosen). Feeds without a title of their own are named after their entry (`serviceName()`).
- A feed whose URL is a download page gets a `datasetLink` `pattern`, whose first capture is the link to a dataset and the optional second its effective date in `dateFormat` (`yyyyMMdd` by default, like the AIRAC datasets of NATS, `d.M.yyyy` for Austro Control); the latest dataset effective today is downloaded, or the first link when the pattern has no date (the Dutch ministry's page). `airac` marks datasets taking effect by AIRAC cycle.
- `refreshHours` makes the scheduler refresh a feed at least that often (`GeoZoneProviders::refreshHours()`), `live` refreshes and outdates it like the live formats (`isLiveUrl()`).
- A service serving its zones by area gets an `areaUrl` template (with the placeholders of `GeoZoneService::resolve()`, like `{bbox}`) and the `coverage` it serves: it is offered by **Download zones for the map area** (`areaProviders()`), for areas up to `maxAreaDegrees`. With `serviceTemplate`, it is also offered by **Add Service...** following the area of interest (`maxAreaKm2`, `note`). `feedArea()` reads the area of its URLs (`bbox`, or an ArcGIS envelope `geometry`). Responses the server limited get their further pages with `paging()` and `pageUrl()`, up to `maxWfsPages`: WFS `GetFeature` URLs by `STARTINDEX` from the counts of the response, ArcGIS queries with a `resultRecordCount` by `resultOffset` while a page says `exceededTransferLimit`, and numbered pages (`page`, like OpenAIP) up to the `totalPages` of the response. A page which fails fails the download, except for WFS responses, whose counts tell the zones missing.
- A service needing credentials, an ED-318 POST or the area of interest is an entry of `services`, offered by **Add Service...** (`serviceTemplates()`): the URL template, a `service` object in the JSON of `GeoZoneService::toJson()` (`method`, `auth`, `authParameter`, `tokenUrl`, `scope`, `headers`, `responseMember`, `areaOfInterest`, `timeWindowHours`, `maxAreaKm2`, `sha256Url`), a `note` telling how to get access, `"supported": false` for services whose data can't be read yet, `nameFromData` for templates whose sources take the title of their data, and the `format` of its responses when they can be empty. The form starts from the fields of a template (`serviceTemplateList()` with `GeoZoneService::toForm()`, another service last), and `GeoZoneManager::serviceFromForm()` builds the service from the template and the fields edited (`GeoZoneService::withForm()`). Secrets are never part of `GeoZoneService` or of catalogues, `GeoZoneCredentials` keeps them.
- Code is only needed for a new format (see [Adding a Format](#adding-a-format)) or a new kind of request or paging.

The names and notes of the built-in catalogue are translated in the context `GeoZoneFeeds.json`: the file declares `"translateKeys": "name,note"` and `"arrayIDKeys": "id"` for `translations/qgc-lupdate-json.py`. Catalogues of manufacturers and operators aren't translated.

`GeoZoneFeedCatalogueLoader`, owned by the repository (`GeoZoneSourceRepository::feedCatalogue()`, also a QML property), applies the overlays on the built-in catalogue with `GeoZoneFeedCatalogue::apply()` and sets the result with `GeoZoneProviders::setCatalogue()`: first the catalogue of the **Feed catalogue URL** setting (`feedCatalogueUrl`), downloaded with the feed refresh interval with conditional requests and kept in `feeds-download.json` for offline starts, then `feeds.json` of the geozone data folder, read again when it changes (both are left alone by `GeoZoneStore`). Entries replace those with the same id, or remove them with `"enabled": false`. A catalogue which can't be read is ignored and an entry which can't be used is left out; `warning()` says which and why, shown in the sources panel, and the built-in catalogue always stays in use. `GeoZoneManager::feedCatalogueChanged` updates the lists of QML.

A custom build can compile in its own catalogue instead of the built-in one with the CMake cache variable `GEOZONE_FEEDS_FILE` (a file in the same format, `-DGEOZONE_FEEDS_FILE=/path/to/feeds.json`), or by editing `GeoZoneFeeds.json`; the overlays still apply on top of it.

`GeoZoneParserTest::_testProviders()` tests the built-in providers and the paging, `_testFeedCatalogue()` the catalogue format, overlays and invalid catalogues, `GeoZoneRepositoryTest::_testFeedCatalogueOverlays()` the catalogue file and URL, `GeoZoneServiceTest` the services with `TestFeedServer` (`_testServiceApiKeys`, `_testServiceOAuth2`, `_testEd318Service`, `_testServiceAreaOfInterest`, `_testMapViewAreaOfInterest`, `_testOpenAipService`), `GeoZoneRepositoryTest` the paging (`_testWfsPaging`, `_testArcGisPaging`), and `GeoZoneParserTest::_testLiveNationalFeeds()` downloads the real services when `QGC_GEOZONE_LIVE_TEST` is set. Add the provider to the national feeds or services listed in the [user guide](../qgc-user-guide/geozones/geozones.md#loading-data) and to the [provider research](geozones-providers.md).

## Operator Zones {#operator-zones}

`GeoZoneOperatorZones` (`src/GeoZone/Planning`, `GeoZoneManager::operatorZones`) keeps the zones operators draw in the Plan View. It edits one zone at a time with a `QGCMapPolygon` or `QGCMapCircle`, which `GeoZoneOperatorZoneEditor.qml` shows with `QGCMapPolygonVisuals` and `QGCMapCircleVisuals` over the Plan View map (from `GeoZonePlanViewOverlay`), and `GeoZoneOperatorZonesSection.qml` lists the zones in the **Geozones** panel (`GeoZoneMapPanel::drawingEnabled`). Saving writes all zones with `GeoZoneEd318Writer` (`src/GeoZone/Core/Formats`) to `operator/my-zones.json` in the storage directory, a subdirectory which `GeoZoneStore::removeOrphanFiles()` leaves alone, reads the document back with `GeoZoneParser` to keep the normalized zones and reject unusable shapes, and loads it with `GeoZoneSourceRepository::loadFile()`, so the zones are a file source keyed by that path like any other (stored copy, packs, alerts, fences). Identifiers (`MY-` and 8 hex digits) are kept across edits. Removing the source removes the file and the zones. `GeoZoneParserTest::_testEd318Writer()` checks that written zones read back identical, `GeoZonePlanningTest::_testOperatorZones()` the editing, the mission check and the persistence.

## Reload Changes and AIRAC Cycles {#reload-changes-and-airac}

`GeoZoneSource::setResult()` compares the zones of a reload with the previous ones: zones are told apart by their identifier, or their name without one (the several shapes of a TFR share it), and compared by the sorted content hashes (`GeoZone::Data::contentHash`) of their shapes. The result is a `GeoZoneSourceChanges` (time, counts and up to `maxNames` sorted names of the zones added, changed and removed), kept until the next reload which changes zones, saved in the index entry (`changes`) and reported by `sourceReport()` as `lastChanges`. The keys of the changed zones (`changedZoneKeys()`) make the monitor alert them again. A reload whose content hash didn't change keeps the zones and the previous changes.

`GeoZoneAirac` computes the AIRAC calendar from the effective date of cycle 2001, 2020-01-02, in steps of 28 days; a cycle is named after the two last digits of the year it takes effect in and its number in that year (`2014` took effect on 2020-12-31, `2101` on 2021-01-28). A provider whose datasets take effect by cycle sets `GeoZoneProviders::Service::airac`; `airacDatasetDate()` reads the effective date of the dataset a feed's download page linked to (the second capture of `datasetLinkPattern`). Such a source shows its cycle and is outdated once `GeoZoneAirac::nextCycleStart()` of its dataset date has come (UTC), whatever the outdated data setting. `GeoZoneSourceVersion::airacCycleOf()` of the briefings uses the same calendar. `GeoZoneRepositoryTest::_testReloadChanges()`, `_testAiracCycles()` and `_testAiracExpiry()` test them.

## Stored Copies and Offline Packs {#stored-copies-and-packs}

`GeoZoneStore` keeps a copy of each source, named with a UUID and the suffix of its content (`GeoZoneStore::fileSuffix()`: `.zip`, `.xml` or `.json`; earlier versions named all copies `.json`), with its parse cache (`.gzc`) next to it. The folder also holds files of others (the authorisations and their backups, the feed catalogues, what a user puts there): the startup cleanup (`GeoZoneStore::removeOrphanFiles()`) and the backup of an unreadable index (`moveToBackup()`) only touch the files the store names itself (`GeoZoneStore::isStoredFileName()`: the UUID names and the `geozones.json` of earlier versions), their caches and the index. Copies are written as `<name>.part` and renamed when complete (`copyFile()`); the cleanup removes what an interrupted copy left, and `clearDownloads()` empties the `downloads` folder of the downloads and pack extractions of the previous session (`GeoZoneRepositoryTest::_testInterruptedCopiesRemoved()`). `sources.json`, written by `GeoZoneSourceIndex`, lists them with their origin, dates, validators, service and provenance. The index is not trusted with other files: an entry is only loaded when `GeoZoneSourceIndex::entryValid()` finds a key, a `file` which is a bare file name rather than a path, and for feeds a `url` equal to the key, and removing a source only deletes a copy the store named itself (`GeoZoneStore::removeFile()`, `GeoZoneRepositoryTest::_testIndexEntriesValidated()`). A copy which a newer one replaces, or whose source is removed, is only deleted by `GeoZoneSourceIndex::save()` once the index without it is written, so that a failed save or a crash in between leaves the index on disk with the copy it names (`GeoZoneRepositoryTest::_testStoredCopyKeptUntilIndexSaved()`). The jobs loading the sources are built by `GeoZoneLoader` (`fileJob()`, `feedJob()`, `downloadJob()`, `storedJob()`, `importedJob()`), so that downloads, stored copies and imported packs carry their dates, validators, area and provenance alike, and `GeoZoneLoader::indexEntry()` turns a job back into its index entry.

`GeoZonePackExchange` writes (with `GeoZoneZip::Writer`) and reads offline packs, zip archives with:

| File | Contents |
| ---- | -------- |
| `manifest.json` | `format` (`qgc-geozone-pack`), `version` (1), `createdAt`, `generator` and `sources`: per source the fields of its index entry (`GeoZoneSourceIndex::entryToJson()`) and of `GeoZoneSourceRepository::sourceReport()`, `file` naming its copy in the pack, and its `service` without custom headers (`GeoZoneService::shareableJson()`). |
| `sources/<name>` | The stored copy of each source, under its name in the store. Packs of earlier versions name all copies `.json`; the content decides how they are read. |
| `signature.json` | In signed packs: `algorithm` (`Ed25519`), `publisher` (the name the publisher gives), `publicKey` (the raw 32 byte key in base64) and `signature` (base64) of the bytes of `manifest.json`. |

The manifest gives the SHA-256 of each copy (`fileSha256`), so the signature of the manifest covers the copies too. Imported copies are checked against it and against the BLAKE2b-256 hash of their provenance; a source with neither is left out, in signed packs too, since nothing then ties its copy to the manifest. Their services follow the rules of [Origins and Credentials](#origins-and-credentials). `GeoZonePackTest::_testOfflinePack()` and `_testStoredFileNames()` test them.

### Pack Signatures {#pack-signatures}

`GeoZonePackSignature` signs and checks with the Ed25519 implementation of OpenSSL's libcrypto, since Qt has no Ed25519. _QGroundControl_ doesn't link OpenSSL otherwise (Qt loads it at run time, and Android bundles the libraries of `android_openssl` for Qt), so signing is optional:

- The CMake option `GEOZONE_PACK_SIGNING` is on by default for desktop Linux, which has the system libcrypto, and off for Windows, macOS, iOS and Android, where it can be turned on when OpenSSL is available to link and deploy. When it is on and `find_package(OpenSSL COMPONENTS Crypto)` finds libcrypto 1.1.1 or later, `src/GeoZone/Core/CMakeLists.txt` links `OpenSSL::Crypto` privately to `GeoZoneCore` and defines `GEOZONE_HAVE_OPENSSL`; otherwise the build goes on without it. Linux builds with it need `libcrypto.so.3` (or `.so.1.1`) at run time, which Qt Network loads anyway for https. The standalone fuzz build turns it off.
- Without it, `GeoZonePackSignature::available()` is false and every function returns before the OpenSSL code: no key is generated or read, nothing is signed and no signature is valid. Packs are exported unsigned, also when the settings shared with other builds name a key; signed packs are imported as `unverified`, without recording their publisher and key, so they are taken as unsigned and are never trusted; the **Pack Signatures** section says so and disables its controls (`GeoZoneManager::packSigningAvailable`).
- `GeoZonePackSignature::ScopedUnavailable` makes `available()` false in builds with OpenSSL, so that `GeoZonePackTest::_testPacksWithoutSigning()` runs the code of builds without it everywhere; the code only builds without OpenSSL lacks is the OpenSSL code itself, which the fuzz build compiles out.

- **Export**: the repository signs with the unencrypted PEM private key (encrypted keys are refused without asking for their passphrase) of the **packSigningKeyFile** setting and gives **packPublisherName** as publisher (`GeoZoneSourceRepository::setPackSigner()`). `GeoZoneManager::createSigningKey()` writes a new key, readable by its owner only.
- **Import**: `GeoZonePackExchange::read()` checks the signature of a signed pack. A signature which doesn't match the manifest makes the whole pack unreadable. Otherwise the provenance of the imported sources records `packSignature` (`unsigned`, `unverified`, `untrusted` or `signed`), `packSigner` (the trusted name, or the name the pack gives) and `packKey`. The integrity recorded in a manifest (`"integrity": "verified"`) is a claim anyone can write: `GeoZoneProvenance::distrustPackIntegrity()` resets it to unchecked for a source imported from a pack which isn't `signed`, at the import, when the trust in its publisher changes, and in `fromJson()` for what earlier versions stored (`GeoZonePackTest::_testPackIntegrityClaims()`).
- **Trust**: **trustedPackPublishers** holds a JSON array of `{ "name", "publicKey" }`, the key in base64 (raw or SubjectPublicKeyInfo) or PEM, see `GeoZonePackSignature::parsePublicKey()`. Changing it re-evaluates the sources imported from signed packs (`GeoZoneSourceRepository::setTrustedPublishers()`), whose signatures were checked at import. Keys are shown by `GeoZonePackSignature::keyId()`, the first 16 hexadecimal digits of their SHA-256.

`GeoZonePackTest::_testSignedPacks()`, skipped without OpenSSL, generates keys and tests signing, the three trust states, trusting a publisher from a source, tampered manifests and replaced copies.

## Origins and Credentials {#origins-and-credentials}

The secrets of the services, their custom headers and the area of interest only go to the server the user configured:

- `GeoZoneOrigin::same()` compares the scheme, host and port of two URLs (the default port of http and https when none is given). `GeoZoneDownloader` sends the `authHeaders` and `authQuery` of its `Options` only to the origin of the first URL of a download, not after a redirect to another origin; `GeoZoneFeedFetch::_optionsFor()` gives the further downloads of a feed (dataset, pages, companions, SHA-256) the service's options only on the origin of the request URL. `GeoZoneService::downloadOptions()` puts the custom `headers` of a service with the credentials, since they may hold keys.
- `GeoZoneService::otherOrigins()` lists the token and SHA-256 URLs which aren't on the origin of the feed. **Add Service...** asks the user to confirm them (`GeoZoneManager::serviceOtherOrigins()`, the `allowOtherOrigins` argument of `addService()`), otherwise the service is refused.
- A secret is kept for the authentication target of its service (`GeoZoneService::sameAuthTarget()`: the authentication and, for OAuth2, the token URL). Setting a service with another target forgets the secret and the token; the OAuth2 token, issued to a client for a scope, is also forgotten when the client id or the scope change (`GeoZoneServiceRegistry::setService()`, `GeoZoneServiceTest::_testTokenFollowsService()`).
- Imported packs never replace the service of a source already known. A new source takes the service of the pack without its `headers`, forgets any secret kept for its URL, and is left out when `otherOrigins()` isn't empty. Feeds are requested at their key, so a pack source whose `url` isn't its `key` is left out too.
- Packs write `GeoZoneService::shareableJson()`, without the headers; the index of the sources keeps them locally.
- A feed added by its address may have a key in it, which is then in its key, its URLs and its provenance. `GeoZonePackExchange::write()` passes every text of a manifest source through `shareableText()`, which replaces the values of the query parameters named like secrets, and the password of the user info, of each web address by `***` (`shareableUrl()`, textually, so that URL templates stay as written). On import, `GeoZoneSourceRepository::importPack()` gives the pack source the key of the feed whose `shareableUrl()` is the key of the pack, which then takes the data and keeps its address. `GeoZonePackTest::_testPackUrlSecrets()` and `_testPackWithoutUrlSecrets()` test it.

`GeoZonePackTest::_testPackServiceTrust()` and `GeoZoneRepositoryTest::_testDownloadRedirects()` test these rules with two `TestFeedServer`s, whose different ports make different origins.

### Credentials Backend {#credentials-backend}

`GeoZoneCredentials` keeps the secret of each source unencrypted in a file of its own, `GeoZoneCredentials.json` in the application data location (`QStandardPaths::AppDataLocation`, the parent of the `GeoZones` folder, so that it is neither stored with the sources nor exported with them), under the SHA-256 of its key: `{ "version": 1, "secrets": { "<sha256>": "<secret>" } }`. Only the owner can read and write the file: it is written through a `QSaveFile` whose permissions are set to owner read and write before the first byte is written, so a file opened to others is closed again by the next write (on Windows, where Qt only maps the read-only attribute, the file relies on the access rights of the user profile). The file is removed with its last secret. A file of a newer `version` is neither read nor replaced, one which can't be parsed is replaced when a secret is entered again; its content is never logged. **Add Service...** says where the secrets are kept.

Earlier versions kept the secrets in the `GeoZoneCredentials` group of the application settings (`QSettings`). Making a `GeoZoneCredentials` moves them to the file, keeping the secrets of the file where both have one, and removes the group once the file is written. `GeoZoneCredentials` has no state: all instances of a name read and write the same file. `GeoZoneServiceRegistry::setSecret()` only keeps a secret for a service which sends one. `GeoZoneServiceTest::_testCredentials()` tests the file, its permissions and the migration under a name of its own.

[QtKeychain](https://github.com/frankosterfeld/qtkeychain) was evaluated as a secure store and deliberately not adopted: on Linux it needs the libsecret development files, falls back poorly without them (only to KWallet and the deprecated GNOME Keyring library), and complicated the builds. The secrets therefore stay unencrypted, protected by the file permissions only; a secure store would need a dependency which builds on all platforms of _QGroundControl_.

## Testing {#testing}

The tests are in `test/GeoZone`, whose `README.md` also describes the fixtures, the fuzzers and the benchmark.

- **One list**: the test classes are listed once, in `test/GeoZone/CMakeLists.txt`, which builds them and adds a CTest test for each class. Each class registers itself at the end of its source with `GEOZONE_TEST(<Class>)` (see `test/GeoZone/GeoZoneTestBase.h`): with QGroundControl's `UnitTest`, not in `UnitTestList.cc`, so that the module needs no changes to the test list of _QGroundControl_, or with `GeoZoneCoreTest`. A new class needs its `.cc` and `.h`, ending with `GEOZONE_TEST(<Class>)`, and its name in one of the lists.
- **Application tests** (`GEOZONE_APP_TESTS`: `GeoZoneManagerTest`, `GeoZoneRepositoryTest` (the sources and their downloads), `GeoZoneServiceTest` (the services and credentials), `GeoZonePackTest` (the offline packs), `GeoZonePlanningTest`, `GeoZoneFenceImportTest`, `GeoZoneRoutePlannerTest`, `GeoZoneMonitorTest`, `GeoZoneFlightTest`) need the application, like the mission controller, MockLink, the map models or the settings, and run in a build with `QGC_BUILD_TESTING` with `QGroundControl --unittest:<Class>` (see [Unit Tests](contribute/unit_tests.md)).
- **Headless core tests** (`GEOZONE_CORE_TESTS`: `GeoZoneEvaluatorTest`, `GeoZoneRouteTest`, `GeoZoneBriefingTest`) test the path evaluator, the route search and the briefing in `GeoZoneCoreTest`, linked with `GeoZoneCore` only: `GeoZoneCoreTest [<Class> [<function>]]`. Tests of the core belong there; their zones are loaded with `GeoZoneTestHelpers::ZoneCatalog`, which loads files into a `GeoZoneSourceRepository` and a `GeoZoneCatalog` like `GeoZoneManager` without the application.
- **Shared tests** (`GEOZONE_SHARED_TESTS`: `GeoZoneParserTest`, `GeoZoneGeometryTest`, `GeoZoneIntentTest`, `GeoZoneReturnTest`, `GeoZoneMissionPathTest`) run both ways; the headless build defines `GEOZONE_CORE_TEST`, which leaves out their parts needing the application (see `GeoZoneTestBase.h`).
- **CTest labels**: all tests of the module are labeled `geozone`, the application tests (named after their class) `app`, the headless ones (named `GeoZoneCore.<Class>`) `core`, `GeoZoneBenchmark` `benchmark` and the fuzz targets `fuzz`. _QGroundControl_ defines its tests in the `test` directory of the build: `ctest --test-dir build/test -L geozone -LE "benchmark|fuzz"` runs all but the benchmark and the fuzzers, `-L core` the headless ones. The application tests share the settings of the application and don't run in parallel.
- **Benchmark**: `GeoZoneBenchmark` measures the core with 10000 synthetic zones: `ctest --test-dir build/test -L benchmark -V`.
- **Fuzzers**: `test/GeoZone/fuzz` has libFuzzer targets for JSON, XML and zip input, built with `-DGEOZONE_FUZZ=ON` or as a project of their own with clang.
- **Time and terrain**: tests depending on the time, the terrain or the QNH set them with `GeoZoneTestHelpers::ScopedEnvironment`, whose clock stands still until the test advances it (`setNow()`, `addSecs()`) and whose terrain is unknown until set (`setTerrain()`). Tests don't read the wall clock, and they pass in other time zones and locales (checked with `TZ=Pacific/Auckland LANG=de_DE.UTF-8` and `LANG=en_US.UTF-8`) and on a single core (`taskset -c 0`). The default units of _QGroundControl_ follow the measurement system of the locale, feet for en_US, so application tests comparing texts with distances set them with `GeoZoneTestHelpers::ScopedMetricUnits` or `_setVerticalUnits()`.
- **Waiting**: tests wait for what they expect, with `QTRY_*` or signal spies, rather than for fixed times. To check that nothing more happens, like an outdated result being dropped, they wait until it can't happen anymore: `_settleWorkers()` waits for the thread pool and delivers the results posted by the workers, `TestFeedServer::settled()` until each request was answered or abandoned by the client.
- **Downloads**: `GeoZoneTestHelpers::TestFeedServer` is a local HTTP server answering by path (`/ok` with the ED-318 fixture, `/missing`, `/broken`, `/empty`, `/hang`), with added files, handlers and delays, which records the requests for the feed, service and refresh tests.

### Validating Files {#validating-files}

`geozone-validate` (`test/GeoZone/tools`, built with the tests and linked with `GeoZoneCore` only) checks geozone files and zip packages the way _QGroundControl_ loads them, without the application or a network: it prints for each file its format and metadata, the number of zones by restriction, their geometry, a summary of their altitude limits by reference and of their schedules, and the warnings of the parsers with the first zones having each, like rings crossing themselves, polygons without area or unknown units. `--zones` lists each zone with its limits, schedule and warnings, `--format` gives the format expected of a feed by its name in the feed catalogue (like `ed318`, `faa-airspace` or `openaip`), `--language` the language of localized texts and `--verbose` shows the log of the parsers. It exits with 1 when a file can't be read or parsed, with `--strict` also on warnings and skipped or missing features, and with 2 on usage errors. Directories are checked file by file, like the fuzz driver reads its corpus (`GeoZoneInputFiles.h`).

```sh
cmake --build build --target geozone-validate
build/Debug/geozone-validate --zones national_zones.json
build/Debug/geozone-validate --strict test/GeoZone/data
```

Its CTest tests, labeled `geozone` and `core`, check the fixtures and the failures.

### Continuous Integration {#ci}

The jobs select the tests by their CTest labels, so a class added to the lists of `test/GeoZone/CMakeLists.txt` runs everywhere without changes to the workflows:

- **Linux** (`.github/workflows/linux.yml`): the debug build runs all unit tests with `--unittest`, which includes the application tests of the module.
- **Geozone** (`.github/workflows/geozone.yml`, weekly and on demand with _Run workflow_ (`workflow_dispatch`)):
  - `sanitizers` builds with AddressSanitizer and UndefinedBehaviorSanitizer and runs `ctest -L geozone -LE "benchmark|fuzz"` but `GeoZoneFlightTest`, whose MockLink copies short strings into fixed size MAVLink fields, which AddressSanitizer reports as overflows. The job fails on any failed test function, crash or sanitizer abort, and on undefined behavior reported in `src/GeoZone`.
  - `fuzz` builds the standalone fuzz project with clang and fuzzes each target for a minute when started by hand; the weekly run fuzzes 20 minutes each and keeps the corpus it grows in the Actions cache for the next runs. Crashes are uploaded as an artifact.
  - `windows-core` builds `GeoZoneCoreTest` and `geozone-validate` with MSVC in a debug build of _QGroundControl_ without GStreamer and runs `ctest -L core`, since the Windows workflow builds releases without tests.
  - `without-geozones` runs `GeoZoneStubCheck`, builds a release of _QGroundControl_ with `-DQGC_DISABLE_GEOZONE=ON` and fails when the binary has strings of the module's classes, see [Building Without Geozones](#building-without-geozones).

::: warning
QML errors are only found at runtime. A component of the module with a missing import or an unknown type still builds, but fails to load, and since the components are placed in views of _QGroundControl_ (like `PlanView.qml` and `FlyViewMap.qml`), the parent view breaks with it. After changing QML, run _QGroundControl_, open the Plan View, the Fly View and the Geozones settings with zones loaded, and check the console for QML warnings.
:::

## Building Without Geozones {#building-without-geozones}

Products without geo-awareness build _QGroundControl_ from the same branch without the module, configured with `-DQGC_DISABLE_GEOZONE=ON` (an option of `cmake/CustomOptions.cmake`, `OFF` by default):

```sh
cmake -S . -B build-nogeozones -G Ninja -DCMAKE_BUILD_TYPE=Release -DQGC_DISABLE_GEOZONE=ON
cmake --build build-nogeozones --target QGroundControl
```

The option is kept in the CMake cache: an existing build directory changes with `-DQGC_DISABLE_GEOZONE=ON` or `OFF` given again. The configure summary shows it as **Disable Geozones**.

What the option leaves out:

- **The module**: all of `src/GeoZone` but `src/GeoZone/Stub`, that is the `GeoZoneCore` library, the application layer, the QML module with its resources and the `GeoZoneManager` settings group. The binary has none of the module's code, QML or settings, only the stub module and the module's icon, which the hidden button of the settings page loads.
- **Its tests**: the classes of `test/GeoZone`, `GeoZoneCoreTest`, `GeoZoneBenchmark`, `geozone-validate` and the fuzz targets. The other unit tests of _QGroundControl_ build and run as usual with `QGC_BUILD_TESTING`.
- **The C++ hooks**, within `#ifndef QGC_DISABLE_GEOZONE` (defined for the whole application by `src/GeoZone/CMakeLists.txt`): `GeoZoneModule::registerQmlTypes()` and `init()` in `QGCApplication`, the toolbar indicator of `QGCCorePlugin::toolBarIndicators()`, the `geoZones` section of plan files in `PlanMasterController` (not written, and ignored when loading a plan saved with geozones) and the checklist of `QGCOptions::preFlightChecklistUrl()`, which is then the upstream `PreFlightCheckList.qml`.

The QML hooks stay unchanged: the QML of _QGroundControl_ still imports `QGroundControl.GeoZone` and places its types (see [Upstream Footprint](#upstream-footprint)), which the stub module of `src/GeoZone/Stub` provides as hidden items doing nothing. `GeoZonePlanViewOverlay.confirmUpload()` uploads at once, its `selectFenceAt()` and `showZonesAt()` and `GeoZoneFlyMapLayer.gotoEntersZones()` return false, `GeoZoneToolStripAction` is hidden and the `GeoZoneManager` singleton hides the Geozones settings page, so the views work like those of upstream _QGroundControl_.

A new hook must keep both builds working:

- In C++, within `#ifndef QGC_DISABLE_GEOZONE`.
- In the QML outside `src/GeoZone`, with its type, the properties it sets and the functions it calls in the stub. The `GeoZoneStubCheck` test (`test/GeoZone/GeoZoneStubCheck.cmake`, labeled `geozone` and `core`, which runs in both builds) fails when the stub lacks a type that QML places, a property it sets or a signal it handles on it, a member it uses through the type's id, or a member of a singleton it reads.

### One Branch for Both Product Lines {#one-branch}

Keep a single branch and build it twice: the products with geozones with the default configuration, the others with `-DQGC_DISABLE_GEOZONE=ON`, like the other options of `cmake/CustomOptions.cmake`. A [custom build](custom_build/custom_build.md) without geozones sets the option in its `custom/cmake/CustomOverrides.cmake`:

```cmake
set(QGC_DISABLE_GEOZONE ON CACHE BOOL "Disable Geozones" FORCE)
```

A custom build can instead keep the module and hide it at runtime with the plugin interfaces of _QGroundControl_, but the module then stays in the binary and zones stored earlier still load and alert. `QGCCorePlugin::overrideSettingsGroupVisibility()` returning false for `GeoZoneManager` (the settings group of `GeoZoneSettings`) hides the Geozones settings page, so that no zones can be loaded, its `toolBarIndicators()` can leave out `GeoZoneIndicator.qml` and `QGCOptions::preFlightChecklistUrl()` can return the upstream `qrc:/qml/QGroundControl/FlightDisplay/PreFlightCheckList.qml`. The other geozone items of the views only show when zones are loaded.

## Upstream Footprint {#upstream-footprint}
